# Build, Test & Release — OMH iOS/iPadOS

This is the release-verification procedure for `OMH.xcodeproj` / `OMH`. An Xcode **build succeeded** result is not equivalent to an **app launched and worked** result.

## Platform and project identity

- Project: generated by `ruby scripts/gen-xcode-project.rb`, named `OMH.xcodeproj`.
- App scheme/target: `OMH`; unit test target: `OMHTests`; UI test target: `OMHUITests`.
- App binary and container: `OMH.app/OMH`.
- IPA artifact: `OpenMind-Harness-unsigned.ipa` (uploaded as the `openmind-harness-unsigned-ipa` Actions artifact).
- Bundle identifier: `app.jackfruit686.openmind-harness`.
- Deployment target: iOS 16.0+, arm64 iPhone/iPad. Simulator architecture is arm64.
- First-party asset catalog: `app/OMHAssets.xcassets`; entitlements: `app/OMH.entitlements`.

Do not rename or delete third-party emulator copyrights and license notices in `ish-arm64/`.

## Local development build (macOS)

Prerequisites: Apple Silicon Mac, Xcode, installed appropriate iPhone/iPad simulators, Ruby `xcodeproj`, Meson, Ninja, LLVM `ld.lld`, Git, network, and the dependencies of the guest rootfs build. The harness is checked out or fetched by the rootfs script.

```sh
make emulator
make rootfs
bash scripts/sync-omh-branding.sh
make project
make app TEAM=YOUR_APPLE_TEAM_ID
```

The `make app` command uses the Makefile's configured Xcode signing mechanism. In CI, the unsigned device build explicitly disables signing. Local physical-device installation requires valid signing/provisioning and a connected device:

```sh
make install TEAM=YOUR_APPLE_TEAM_ID DEVICE=YOUR_DEVICE_UDID
make run TEAM=YOUR_APPLE_TEAM_ID DEVICE=YOUR_DEVICE_UDID
```

Run simulator tests on installed runtimes:

```sh
make test-sim SIM="$(scripts/pick-simulator.sh)"
# Or pick an iPhone simulator for platform-specific smoke tests:
make test-sim SIM="$(scripts/pick-iphone-simulator.sh)"
```

A full `make test` also runs emulator and guest-rootfs tests. See `Makefile` for all targets.

## GitHub Actions workflow

[Build unsigned IPA](https://github.com/tjcrims0nx/omh-iOS/actions/workflows/build-ipa.yml) runs on pushes to `main` and `rebrand/omh` and can be started manually. Validate the **exact head SHA** you plan to merge/release:

| Gate | Required evidence |
| --- | --- |
| `validate-port` | Node static regression suite passes |
| `build` | Rootfs/build checks pass, Xcode device build succeeds, IPA uploaded |
| `simulator-smoke` | iPad simulator boots, app launches, iPad UI test passes |
| `iphone-simulator-smoke` | iPhone simulator boots, native iPhone dashboard/editor and log tests pass |

CI is configured to upload UI diagnostics/screenshots. Check the run's artifact list; missing screenshots or skipped jobs invalidate any claim of visual verification. The build's unsigned IPA artifact is separate from both simulator test results.

Static checks specifically assert native UIKit controller names, state API usage, navigation selectors and layout constraints; the on-screen appearance must still be checked by XCUITest artifacts or physical-device testing.

## Inspecting an unsigned IPA

Download the `openmind-harness-unsigned-ipa` artifact from the selected Actions run and extract the IPA archive. The expected payload includes `Payload/OMH.app/OMH` and `Payload/OMH.app/root.tar.gz`. If the local file is `OpenMind-Harness-unsigned.ipa`, run:

```sh
bash scripts/verify-omh-ipa.sh OpenMind-Harness-unsigned.ipa
```

The verifier rejects the legacy `Payload/DSH.app` bundle and checks required guest runtime, MCP, dashboard and sandbox-diagnostic files. This checks packaging, **not** safe isolation, successful on-device operation or provider authentication.

## Runtime, sandbox, and MCP

The guest starts local runtime/dashboard services behind a loopback address. `omh-runtime status` and `omh-runtime doctor` can help diagnose the running guest. Bubblewrap is installed but the emulated iSH kernel may not support its namespace/mount operations: `omh-sandbox-check` must verify them, and failed isolation checks must never be advertised as successful. Vercel OAuth MCP connectivity and optional HTTPS/live adapters need their own explicit configuration and credentials.
